# 归档外部可靠触发方案（未实施）

> 目的：GitHub Actions 的 `schedule` 触发在实测中会延迟 4–10 小时，`archive.yml` 的 `*/30` 实际中位间隔 292 分钟。本方案用一个外部定时器调用 `workflow_dispatch`，把“班次结束后必须有一次运行”从概率问题变成确定问题。
> **本文只写方案，不创建、不索要、不保存任何 token。**

## 1. 为什么不用 GitHub cron 兜底

- `schedule` 是尽力而为，GitHub 官方不保证准时；仓库越冷、整点越挤，延迟越大。
- 归档脚本本身已经改成数据驱动，能容忍数小时延迟；但数据端在 **次日 00:00 清掉白班桶**，所以白班必须在 20:20–24:00 之间至少跑一次。
- 需要的是“每天两个固定时间点各一次”的可靠触发，而不是更高频的 cron。

## 2. 方案：Cloudflare Worker Cron Trigger

Cloudflare Workers 的 Cron Trigger 独立于 GitHub，免费额度足够每天 2–6 次调用。

### 2.1 需要用户提供的东西（夜里不创建）

1. 一个 GitHub **fine-grained personal access token**：
   - 仅限仓库 `wlp713/pdtiii-live`；
   - 仅勾选 **Actions: Read and write**（`actions:write`）；
   - 有效期建议 90 天，到期前更换；
   - 不要给 `contents`、`secrets`、`admin` 权限。
2. Cloudflare 账号下新建一个 Worker（或复用现有 Worker），以及一个 Cron Trigger。

### 2.2 Worker 逻辑

```js
// 伪代码；真实实现只需要 fetch，不需要任何 npm 依赖
export default {
  async scheduled(event, env, ctx) {
    const response = await fetch(
      "https://api.github.com/repos/wlp713/pdtiii-live/actions/workflows/archive.yml/dispatches",
      {
        method: "POST",
        headers: {
          "Authorization": `Bearer ${env.GITHUB_ARCHIVE_TOKEN}`,
          "Accept": "application/vnd.github+json",
          "X-GitHub-Api-Version": "2022-11-28",
          "User-Agent": "pdtiii-archive-cron"
        },
        body: JSON.stringify({ ref: "main", inputs: { shift: "auto" } })
      }
    );
    if (!response.ok) {
      // 让 Worker 日志/告警能看到失败；不要把 token 打进日志
      console.error("dispatch failed", response.status, await response.text());
      throw new Error("dispatch failed");
    }
  }
};
```

### 2.3 Cron 表达式（UTC）

泰国时间 = UTC+7：

| 目标（泰国） | UTC cron | 说明 |
|---|---|---|
| 20:35（白班结束后 15 分钟） | `35 13 * * *` | 白班数据在 00:00 前有效，20:35 最稳 |
| 07:55（夜班结束后 5 分钟） | `55 0 * * *` | 夜班 07:50 结束，07:55 抓边界 |
| 可选 22:35 兜底 | `35 15 * * *` | 白班第一次失败时再试一次 |

只保留 20:35 和 07:55 两次即可；`archive.yml` 仍保留 `*/30` 作为兜底，两者不冲突（`concurrency` 已串行化）。

### 2.4 配置步骤（用户执行）

1. GitHub → Settings → Developer settings → Fine-grained tokens → 新建 token（权限见 2.1）。
2. Cloudflare Dashboard → Workers & Pages → 新建/选择 Worker → Settings → Variables → 添加 **Secret** `GITHUB_ARCHIVE_TOKEN`，值粘贴 token。
3. 部署 2.2 的 Worker 代码。
4. Settings → Triggers → Cron Triggers → 添加 `35 13 * * *` 和 `55 0 * * *`。
5. 在 Worker 的 Logs 里确认第一次 `scheduled` 返回 204；在 GitHub Actions 里确认出现 `workflow_dispatch` 运行。
6. 把 token 到期日写进交接书；到期前更换 Secret，不需要改代码。

## 3. 安全与失败处理

- token 只存 Cloudflare Secret，不写进仓库、不写进 `wrangler.toml`、不写进前端。
- Worker 只允许调用这一个仓库的这一个 workflow；不要做成通用代理。
- `workflow_dispatch` 的 `ref` 固定 `main`；不要接受外部传入的 ref/inputs。
- GitHub 返回 401/403 时 Worker 抛错，Cloudflare 的 Cron 失败会发邮件/告警；不要静默重试到无限。
- 如果 token 泄露：立即在 GitHub 撤销，更新 Cloudflare Secret；归档本身只读 Firebase + 写 `history/`，没有生产数据写入权限。

## 4. 验收标准

- 连续 3 天在 20:35 和 07:55 各出现一次 `workflow_dispatch` 运行；
- 运行结论为 success，且 `history/shifts/` 新增对应班次文件；
- 若某个班次源数据不可用，运行结论为 failure（脚本返回 2），而不是静默成功；
- 不出现 `main` 被 force push、不出现并发写冲突。

## 5. 备选方案（不推荐）

- **GitHub 仓库里的第二个 workflow 用 `schedule` 调 `workflow_dispatch`**：仍然依赖同一个不可靠调度器，没有解决根因。
- **本机 Windows 计划任务调 GitHub API**：依赖开发机开机/联网，交接书已明确不作为主链路。
- **Cloudflare Worker 直接写 `history/`**：需要给 Worker 仓库写权限，权限过大，且绕过了单测与提交审计。
