## 0. 结论摘要

1. **白班大面积缺失的直接根因不是 cron，而是归档脚本自己把 `comparable` 班次丢掉了。** `current_shift_documents()` 允许 `complete`/`comparable`，但 `main()` 只写 `status == "complete"`。2026-10-07 起 Press C-Shaft 只剩 08:00 一个桶，白班覆盖从 39/39 变成 38/39，状态降为 `comparable`，于是每天都被 `SKIP`。10-06 的白班仍能写入，10-07 起全部消失，时间点完全吻合。
2. **cron 确实不可靠，但它是次要原因。** 2026-09-27 至 2026-11-07 的 41 天里，`archive.yml` 只有 200 次定时运行（按 `*/30` 应有约 1967 次），中位间隔 **292 分钟**、最大 **575 分钟**。数据驱动逻辑能在滚动缓冲内自愈，但白班数据在 **次日 00:00 后会被数据端清掉**，所以 20:20–24:00 没有运行就真的丢了。
3. **迟到运行会串档。** `2026-10-12-night.json` 的 `productionDate` 写成了 `2026-10-13`，导致 `history/index.json` 里 10-12 消失、10-13 多出一份来源不明的夜班。修复后该文件被隔离为 `invalid`，不再参与分析。
4. **旧快照的 `quality.status` 不可信。** 多份早期文件 `coveredLines=0` 却标 `complete`（如 10-11-night、10-12-night）；本次新增的完整性校验不会覆盖旧文件，但会在健康摘要里按真实覆盖重新标记。
5. **本次自愈补回 16 个白班**（从同日晚间/夜班快照重建），并显式写出 **14 个缺档占位**（12 个白班 + 2 个夜班）。补回的白班全部标 `partial`（38/39 线，Press C-Shaft 或 Motor CL 缺失），没有一份被标成 `complete`。
6. **夜班前半夜桶冻结是数据端 bug**（`d=2026-09-11`），本次归档按 `d` 过滤，不再把冻结桶并进当天；代价是夜班明细缺前半夜，质量记录为 `bucketDateMismatch` 警告，产量汇总仍取 00:30–07:50 的正确累计值。

### 1.2 白班缺失的直接根因（可复现）

```text
2026-10-06 白班文件: status=complete mapped=39 covered=39 captured=23:08
2026-10-07-night.json 里同一天白班: dayStatus=comparable dayCovered=38/39
  Press C-Shaft 的 lastDayMinute=480（只有 08:00 桶），不计入覆盖
2026-10-07 白班文件: 不存在
```

`scripts/archive_daily.py` 旧 `main()`：

```python
if document["quality"]["status"] != "complete":
    print(f"SKIP {shift} {production_date} status=...")
    continue
```

而 `current_shift_documents()` 的准入是 `("complete", "comparable")`。两处口径不一致：白班从 10-07 起稳定落在 `comparable`，于是每天都被跳过；夜班因为 `nightExpectedLines` 会按实际有夜班桶的线数自适应，所以一直是 `complete`。这解释了“白班 24 份、夜班 55 份，且 10-25 之后每天只有夜班”的现象。

### 1.3 数据端滚动窗口

```text
2026-11-07 23:45 实测 pdtiii.json:
  2026-11-06 00:30–07:50 桶存在（11-06 夜班的凌晨段）
  2026-11-07 08:00–20:20 桶存在（11-07 白班，actual 全 0、plan 非 0）
  2026-11-07 20:30–23:30 桶的 d 全是 2026-09-11（冻结）
2026-11-08 00:16 再测:
  11-07 白班桶已全部消失，只剩冻结的 20:30–23:30 桶
```

结论：**白班必须在次日 00:00 前归档；夜班在次日 00:00 前仍可归档**。旧设计把白班窗口压到 20:20–20:29（10 分钟）过于苛刻，但完全去掉窗口也不行——本次改为“按桶判断 + 源日期校验 + 00:00 前尽量补”，并在超时后写 `missing` 占位。

### 1.4 夜班前半夜桶冻结

`2026-11-07 23:12` 与 `2026-11-08 00:16` 两次实测，所有线体的 `h=2030/2130/2230/2240/2330` 桶 `d` 均为 `2026-09-11`，而 `h=30…750` 的 `d` 正常。根因是 `sync_db.py` 的“同一桶只保留最早记录”规则把 9/11 的旧桶永久保留，详见 `design/给数据端_夜班前半夜桶冻结修复.md`。本次**不修数据端**，归档侧按 `d` 过滤并记录问题。

## 5. 本次归档加固的判定规则（供页面/后续核对）

| 状态 | 条件 |
|---|---|
| `complete` | 映射线体 ≥ 有效预期线体，且 ≥34 条线到达班次末桶，且无阻断性 issue |
| `partial` | 数据可用，但存在线体不足、累计回落、全零实际、起点桶残留等阻断性 issue；仍然写入快照 |
| `missing` | 没有可用数据，或数据不足 34 条线/未到班次末桶；只写占位与原因 |
| `invalid` | 文件日期与 `productionDate` 不一致，或文件损坏；隔离，不参与分析 |

警告性 issue：`bucketDateMismatch`、`startCarryover`、`idleLines`、`earlyStoppedLines`。
