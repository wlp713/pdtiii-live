从数据库取数写进 Firebase（这是稳定底座）。现在要你**自主整合出一套最稳、不重复、不冲突**的生产日归档方案。
你能直接看到这台机器上全部真实代码和运行环境，所以**最终判断权在你**——本指令只给分析框架、既定事实和红线，不替你硬定细节。

## 〇、任务本质（一句话）
把"生产日归档"做成：**每 5 分钟探一次源数据 → 白班/夜班各自数据完整就归档 → 与现有脚本不冲突、不重复、不覆盖**。

## 一、三条【绝对红线】（宁可不做，不可破坏）
1. **绝不改 `sync_db.py` 取数主逻辑**（含 Frame No.1~5 白名单、段边界桶 `HOURLY_BOUNDARY_BUCKETS`、60s 省流量）。只加新文件/加 cron 行，**不许删它任何备份、不许整份覆盖**。
2. **hourly 段边界桶 (29 个) 不变**：白班末 `2020`、夜班末 `750` 是归档判定的命门。
3. 现有取数 cron 行**一行不许改**，只能**追加**归档行。

====================================================================
## 二、归档脚本（已有，纯标准库，可复用）
`scripts/archive_daily.py` 用的全是 Python 标准库（urllib/json/argparse/datetime），**无需装包**。
入口：`python3 scripts/archive_daily.py --shift auto`
核心逻辑 = **数据驱动**（不看墙钟，只看源数据完整度）：
- 白班源桶到 `2020`(20:20) 完整 → 归档 `{D}-day.json`
- 夜班 <08:00 晨桶到 `750`(07:50) → 归档 `{D-1}-night.json`
配套 `scripts/history_analytics.py`（判定 + 汇总）。

====================================================================
## 三、时段划分（归档必须存的字段——产出分析界面靠它们）
每班归档**必须同时存下 正常段 + 加班段**（产出分析界面的"加班段产出"列读的就是 `overtime`）：
- **白班** = 桶在 `08:00(480) ~ 20:20(1220)`：
  - 正常段 `normal` = 最后一个 ≤`17:20(1040)` 的桶值
  - 加班段 `overtime` = 末桶(≤20:20)值 − `normal`（≥0）
  - `total` = `normal + overtime`
- **夜班** = 桶在 `<08:00`（凌晨 `30~750`）：
  - 正常段 `normal` = 最后一个 ≤`05:50(350)` 的桶值
  - 加班段 `overtime` = 末桶(≤07:50)值 − `normal`
  - `total` = `normal + overtime`
- 归档 JSON 里这些字段：`normal` / `overtime` / `total` / `plan` / `attainment(正常/计划)`。

**完整判定标准**（决定"这个班能不能归档"）：
- **complete**：mapped≥39 且 covered≥39（末桶到 ≥20:10 白班 / ≥07:40 夜班）
- **comparable**：mapped≥34 且 covered≥34（也归档）
- 达不到 → `partial` → **不归档**（宁可不存，不存坏的）
- 白班夜班分属：白班=源当天，夜班=源前一天。

## 四、你必须自己排查/裁定的冲突点（这是"自主判断"的关键）

我在开发机 (19777) 侧已发现 3 个潜在隐患，但这台机器上可能有差异，**你必须在现场核验后裁定**：

### 冲突点 1：两个归档器会不会重复/并发写同一文件？
现有 cron 里可能有：
- `10 21 * * * ... ensure_daily_archive.py`（每天 21:10）
- 以及 20:31/08:00 或我建议的 `*/5` 归档。
`ensure_daily_archive.py` 和 `archive_daily.py` 都会重建 `history/{date}.json`，且都会 commit+push。
请核查：**它们会不会同时写同一文件 / 重复 commit / 覆盖窗口**。
→ 若会，裁定方案：**收敛成单套**（只留 archive_daily + 每5分钟探针；ensure 降级为"纯检查不补跑"或停它的 21:10 cron），或**错峰**（ensure 稳在 21:10 且不再写 shifts/，只兜底重建 daily artifact）。由你判断哪个在这台机器最稳。

### 冲突点 2：判定口径不一致
`ensure_daily_archive.py` 的"完整"只看白班覆盖到 ≥20:10 且 ≥30 线，**完全不看 night/normal/overtime** → 可能漏补夜班或误判。
请裁定：是否让所有归档统一走 `archive_daily.py` 的数据驱动口径（dayStatus/nightStatus），避免两套口径打架。

### 冲突点 3：git push 凭据 / 仓库位置
这台机器上 `pdtiii-live` 仓库在哪、git remote 有没有 push token？
- 有 → 归档后 commit+push 上线
- 无 → **只生成文件 + 本地 commit，不 push**（把 push 留给开发机/GitHub 兜底），别因 push 失败中断归档。
